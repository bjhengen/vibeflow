## Issue #6 — New tabs should auto-fit the window width

### Problem
A newly spawned tab is initialized with hard-coded `DEFAULT_COLS = 80 × DEFAULT_ROWS = 24`
(`session.rs`) and is **not** resized to the live window. It only corrects itself on the next
`WindowEvent::Resized`. The first tab gets it right because `resumed()` resizes it immediately
after spawn; subsequent tabs (keyboard `Shortcut::NewTab` and click `TabBarHit::NewTab`) skip
that step. The keyboard path additionally never requests a redraw.

### Root cause
The resize block — `renderer.surface_size()` → `cell_pitch()` → subtract tab-bar height →
`pixels_to_grid()` → `app.resize_all(rows, cols)` — exists in `resumed()` and the
`WindowEvent::Resized` handler, but is not invoked on new-tab creation.

### Fix
1. Extract the resize block into a single helper on `WindowApp`:
   ```rust
   /// Resize every session's PTY + grid to the current window dimensions.
   /// No-op if the renderer isn't ready yet. Logs on failure.
   fn resize_all_to_window(&mut self) { /* renderer surface_size + cell_pitch
       + tab_bar_height_px → pixels_to_grid → app.resize_all */ }
   ```
2. Call `self.resize_all_to_window()` after a successful `new_tab()` in **both** new-tab paths:
   - `window.rs` ~929 `TabBarHit::NewTab` (click)
   - `window.rs` ~967 `Shortcut::NewTab` (keyboard)
3. Refactor `resumed()` and `WindowEvent::Resized` to call the same helper (eliminates the
   existing duplication; net behavior unchanged for those two sites).
4. The helper performs the resize only — it does **not** request a redraw. Redraw stays the
   caller's responsibility: the click path already calls `window.request_redraw()` after
   `new_tab()` and keeps it; the keyboard `Shortcut::NewTab` path gains a `request_redraw()`
   (which it currently lacks). `resumed()`/`Resized` retain their existing redraw behavior.

### Testing
The winit window/renderer plumbing is not unit-testable without a GPU surface. The grid-sizing
logic (`pixels_to_grid`) and `App::resize_all` already have coverage. New-tab fit is verified by
VNC smoke walk: open a wide window, Ctrl+Shift+T (or click `+`), confirm the new tab's content
fills the full width immediately (no narrow column that only fixes on manual resize).

## Issue #7 — Waiting state times out to dull-gray "active"

### Problem
On a Claude Code tab detected via the **Tier-3 `/proc` heuristic** (i.e. the OSC 1338 / OSC 133
shell hooks are *not* installed), the AI-state indicator follows:

```
Working → (heuristic_silence, default 4 s output silence) → Waiting (amber)
        → (stale_state, default 30 s) → Active
```

`Active` renders as a transparent indicator with subtitle "active" (`tabs.rs:554`,
`session.rs::subtitle_for`). So the amber "needs you" cue silently disappears ~30 s after Claude
stops emitting, even though Claude is genuinely still waiting on the user — defeating the
headline feature.

### Why the explicit path is unaffected
For OSC 1338 self-reporting sessions (`explicit_seen == true`), `tick()` returns early while the
session is authoritative, and the `explicit_stale_state` fuse (default 300 s) deliberately
**holds** amber for `Waiting` by nulling `last_event_at` (`tracker.rs:208-237`). The bug is
specific to the Tier-3 heuristic path, which has no such persistence and no recovery transition.

### Design decisions (confirmed with user)
- **Recovery trigger: output resumes only.** Amber persists indefinitely until Claude produces
  output again, at which point the tab returns to `Working`. Symmetric with the existing
  `Working → Waiting` silence rule; uses instrumentation already in place.
- **Change C included:** when the AI tool *exits* (foreground-process heuristic flips
  active→inactive) while the tab is in Tier-3 `Waiting`, clear to `Active` — "the AI tool is
  gone, nothing left to respond to." Prevents a new stuck-amber-on-bare-shell case.

### Changes — `tracker.rs`
- **A** (`:262`): exempt `Waiting` from the `stale_state` demotion.
  `if self.state != TabState::Active && self.state != TabState::Waiting`.
  `Working`/`Idle`/`Done` keep the 30 s reset.
- **B** (`:167`): add `TabState::Waiting` to the `OutputObserved` heuristic-promotion match, so
  resumed output recovers `Waiting → Working`. Already gated `!explicit_seen && heuristic_active`,
  so it touches only the Tier-3 path.
- **C** (`:276`): change `set_heuristic_active(&mut self, active: bool)` to return `bool`. On the
  active→inactive edge, if `!explicit_seen && self.state == Waiting`, set `state = Active` and
  return `true`. Explicit sessions are exempt (their persistence is governed by the fuse).

### Changes — `session.rs` (event wiring)
State changes that occur **outside** `tracker.tick()` must emit `SessionEvent::StateChanged` so
the tab repaints **and** the cached subtitle string refreshes (otherwise the stripe color updates
via the unconditional `TermUpdated` but the subtitle text stays stale).

- `poll()` `PassThrough` arm (`:347`): capture the `OutputObserved` return; on `true`, call
  `refresh_default_subtitle()` and push `StateChanged`. (Also fixes a pre-existing latent
  staleness for the Active→Working heuristic promotion on the same line.)
- `tick()` (`:412`, `:425`): OR the `set_heuristic_active` return (Change C) and the rising-edge
  `OutputObserved` return with `tracker.tick(now)` when deciding to emit `StateChanged`.
- `PtySession::set_heuristic_active` wrapper (`:435`): propagate the new `bool` from the tracker.

### Testing (TDD)
`tracker.rs` unit tests:
1. Tier-3 `Waiting` survives past `stale_state` (state still `Waiting` after >30 s with no input).
2. `OutputObserved` while Tier-3 `Waiting` + `heuristic_active` ⇒ `Working` (returns `true`).
3. `set_heuristic_active(false)` while Tier-3 `Waiting` ⇒ `Active` (returns `true`); and a
   no-op/`false` when not Waiting or when `explicit_seen`.
4. Regression: explicit-path `Waiting` persistence after the fuse is unchanged.

`session.rs` test:
5. `poll()` emits `StateChanged` (not just `TermUpdated`) when resumed output recovers a Tier-3
   `Waiting` tab to `Working`, and the subtitle becomes "working".

Note: per `lesson_subprocess_detection_tests`, subprocess-spawning tests run serially
(`cargo test --lib -- --test-threads=1`) for the full suite. The new tracker tests are pure-logic
(injected `now`) and do not spawn processes.

### Known residual (out of scope, accepted)
A Tier-3 `Waiting` tab whose AI tool stays foreground but never emits again holds amber until
the user acts and the AI responds — intended "needs you" semantics. The explicit-path comments
(`tracker.rs:218-237`) document the analogous behavior.
