## 1. Scope & non-goals

**In scope (v0.1.1):**

1. **npm `prepack` script** (Codex #1): `bindings/npm/package.json` lacks a
   `prepack` / `prepublishOnly` script, so `npm pack` from a clean checkout
   produces a package containing only `README.md` + `package.json`. The
   currently-published `vibeflow-protocol@0.1.0` is healthy by accident
   (publish was done from a working tree with `dist/` already built); the
   next publish from anywhere else would ship a broken package. Add
   `prepack` and `prepublishOnly` scripts.
2. **LICENSE files in published Cargo crates and npm package** (Codex #3):
   verified — `cargo package --list -p vibeflow` and `-p vibeflow-protocol`
   include only `README.md` (and the JetBrains font license in `vibeflow`).
   `cargo` does not automatically pull workspace-root files into individual
   crate packages. Same gap on npm — `files` array doesn't include the
   LICENSE files. Add LICENSE files to each crate dir (per-crate `include`
   directive in `Cargo.toml`, or symlinks) and to `bindings/npm/package.json`
   `files`.
3. **Remove OSC 52 claim from README** (Codex #5): verified — `session/osc.rs`
   handles OSC 0/1/2/133/1338 but not 52. `README.md`'s features bullet
   claiming "clipboard via OSC 52 and arboard" is currently false. Remove
   the OSC 52 phrasing (keep the arboard claim). **Actual OSC 52
   implementation is deferred** — it has real permission/security design
   work (size limits, base64 validation, user-prompt or allow-list policy).
4. **Strip `ESC[201~` from clipboard paste** (Codex #4): real
   terminal-security gap. Bracketed paste mode wraps pasted content with
   `ESC[200~` + content + `ESC[201~`. If the content itself contains
   `ESC[201~`, a malicious paste can "close" the bracketed-paste frame and
   inject arbitrary terminal input executed as typed-by-user. Standard fix:
   strip `ESC[201~` from pasted content before sending to the PTY. Applies
   to both clipboard paste paths in `window.rs` (regular clipboard and
   primary selection).
5. **`appimagetool` SHA256 pin in `release.yml`** (Codex #2, narrowed):
   currently the workflow downloads `appimagetool-x86_64.AppImage` from
   `github.com/AppImage/appimagetool/releases/download/${VERSION}/...` and
   `chmod +x` + executes it with no integrity check. Add a SHA256
   verification step before the executable bit is set. Also publish a
   `vibeflow-x86_64.AppImage.sha256` alongside the AppImage in the GitHub
   Release for downstream verification. **Defer** full action-SHA pinning
   (it imposes friction for action updates, and the project doesn't yet have
   a dependency-bot flow to manage that).
6. **Add packaging assertions to `ci.yml`** (Codex #10): `cargo
   package --list -p vibeflow-protocol` and `-p vibeflow` should each be
   inspected for the presence of LICENSE-MIT, LICENSE-APACHE, and README.md
   on every CI run. `npm pack --dry-run --json` from `bindings/npm/` should
   be inspected for `dist/src/index.js`, `dist/src/index.d.ts`,
   `LICENSE-MIT`, `LICENSE-APACHE`, and `README.md`. CI fails on any
   missing required file. This catches Codex #1 / #3 / #5 going forward.
7. **`FORCE_JAVASCRIPT_ACTIONS_TO_NODE24: true` env in `release.yml`**
   (carried from v0.1.0 follow-up list — silences the Node 20 deprecation
   warning that fired on the v0.1.0 release run; matches `ci.yml`).

**Out of scope (deferred, with rationale):**

- **Codex #2 — pin GitHub Actions to commit SHAs.** Higher friction for
  action updates, lower marginal value than checksum-verifying downloaded
  binaries; revisit if/when we adopt dependency-bot automation.
- **Codex #7 — glyph atlas eviction.** Real long-tail crash risk but
  non-trivial (LRU + stress tests). Defer to v0.2 or a dedicated perf pass.
- **Codex #8 — config / theme input bounds.** Low practical DoS risk
  (theme imports are user-initiated, config is user-owned). Add bounds
  opportunistically when other config work happens.
- **Codex #9 — idle-redraw optimisation.** Architectural change to redraw
  scheduling. Real wins on battery devices but not a correctness issue.
  Defer to v0.2 perf pass.
- **OSC 52 implementation** itself — defer; the README fix only removes a
  false claim, not the feature gap.

## 2. Per-fix design

### 2.1 npm `prepack` + `prepublishOnly`

`bindings/npm/package.json` `scripts` section gains:

```json
"prepack": "npm run build",
"prepublishOnly": "npm test"
```

`prepack` runs before `npm pack` (and therefore before `npm publish`),
ensuring `dist/` exists. `prepublishOnly` runs only on `npm publish` and
runs the full test suite — a final gate that catches breakage before an
irreversible publish.

**Verification:** from a clean checkout (no `dist/`, no `node_modules/`),
`npm pack --dry-run --json` must list `dist/src/index.js`,
`dist/src/index.d.ts`, plus README and package.json.

### 2.2 LICENSE files in Cargo + npm packages

**Cargo (both crates):** the cleanest approach is per-crate **symlinks**
to the workspace-root LICENSE files. Cargo follows symlinks when
packaging, the workspace-root files remain canonical, and we avoid
duplicate-file maintenance. Create:

- `crates/vibeflow/LICENSE-MIT` → `../../LICENSE-MIT`
- `crates/vibeflow/LICENSE-APACHE` → `../../LICENSE-APACHE`
- `crates/vibeflow-protocol/LICENSE-MIT` → `../../LICENSE-MIT`
- `crates/vibeflow-protocol/LICENSE-APACHE` → `../../LICENSE-APACHE`

`cargo package` includes symlinked files in the published `.crate`. If
symlinks misbehave on a contributor's Windows checkout, the per-crate
`include = ["src/**/*", "README.md", "LICENSE-MIT", "LICENSE-APACHE"]`
in each crate's `Cargo.toml` is the fallback (file-copy approach).
Implementer's judgement at execution time, defaulting to symlinks.

**npm:** `bindings/npm/package.json` `files` array gains
`"LICENSE-MIT"` and `"LICENSE-APACHE"`. Create `bindings/npm/LICENSE-MIT`
and `bindings/npm/LICENSE-APACHE` as symlinks to the workspace-root files
(or copies, same trade-off as Cargo).

**Verification:** the CI assertions added in §2.6 cover this going forward.

### 2.3 OSC 52 claim removal from README

In `README.md`'s "Features (v0.1)" bullet list, the current line:

```
- Block (Alt+drag) and shift-extend selection; clipboard via OSC 52 and arboard.
```

becomes:

```
- Block (Alt+drag) and shift-extend selection; clipboard via arboard.
```

Same edit in `crates/vibeflow/README.md` if the OSC 52 claim appears there
(it does not, per the spec; verify before editing). The CHANGELOG `[Unreleased]`
section gains an entry under `### Fixed` documenting that the README no longer
claims an unimplemented feature.

### 2.4 Strip `ESC[201~` from paste paths

Two paste paths in `crates/vibeflow/src/window.rs` send clipboard content
to the PTY:

- Regular clipboard paste around line 688 (per Codex review).
- Primary selection paste around line 714.

Both should pass clipboard text through a small sanitiser that **removes**
all occurrences of the bracketed-paste end marker `ESC[201~` (bytes
`\x1b\x5b\x32\x30\x31\x7e`). Removal not replacement — substituting with
`?` or similar still produces no visible artifact, but removal preserves
adjacent content unambiguously.

New helper, e.g. `fn sanitise_paste(input: &str) -> String`, lives next
to the existing paste code (or in `clipboard.rs` if cleaner). Returns a
sanitised owned `String`. Three tests minimum:

- happy path: input without the marker passes through unchanged
- input containing a single `ESC[201~`: marker removed, surrounding content
  preserved exactly
- input containing multiple markers (including back-to-back): all removed

**Out of scope for this fix** (per Codex's "consider"): warning/confirming
on ESC or C0 control content. Stripping just the bracketed-paste end
marker addresses the concrete injection vector; broader paste-prompting
needs UX design and is deferred.

### 2.5 appimagetool SHA256 verification

`.github/workflows/release.yml` "Download appimagetool" step becomes a
download + verify step. The expected SHA256 is pinned in the workflow
env as `APPIMAGETOOL_SHA256: "<hex>"` next to `APPIMAGETOOL_VERSION`.
The implementer computes the expected SHA256 at plan-execution time by
downloading the binary once (manually, locally) and recording the hash;
the value is then baked into the workflow.

```yaml
- name: Download appimagetool (verify SHA256)
  run: |
    set -euxo pipefail
    curl -fSL -o appimagetool \
      "https://github.com/AppImage/appimagetool/releases/download/${APPIMAGETOOL_VERSION}/appimagetool-x86_64.AppImage"
    echo "${APPIMAGETOOL_SHA256}  appimagetool" | sha256sum -c -
    chmod +x appimagetool
```

The workflow also publishes `vibeflow-x86_64.AppImage.sha256` alongside
the AppImage in the GitHub Release, so downstream users can verify the
artifact they download. A new step before the release-create step:

```yaml
- name: Publish AppImage checksum
  run: sha256sum vibeflow-x86_64.AppImage > vibeflow-x86_64.AppImage.sha256
```

…and the `softprops/action-gh-release@v2` `files:` list gains the `.sha256`.

### 2.6 CI packaging assertions

`.github/workflows/ci.yml` gains a new `packaging` job (parallel with the
existing `rust`, `fuzz`, `npm` jobs):

```yaml
packaging:
  name: Packaging assertions (Cargo + npm)
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - name: Install stable toolchain
      uses: dtolnay/rust-toolchain@stable
    - name: Cargo cache
      uses: Swatinem/rust-cache@v2
    - name: Use Node.js 22 (current LTS)
      uses: actions/setup-node@v4
      with:
        node-version: "22"
        cache: "npm"
        cache-dependency-path: bindings/npm/package-lock.json

    - name: Verify Cargo packages include LICENSE-MIT, LICENSE-APACHE, README.md
      run: |
        set -euxo pipefail
        for crate in vibeflow-protocol vibeflow; do
          for required in LICENSE-MIT LICENSE-APACHE README.md; do
            cargo package --list -p "$crate" | grep -qE "(^|/)${required}$" \
              || { echo "::error::missing $required in cargo package -p $crate"; exit 1; }
          done
        done

    - name: Verify cargo publish --dry-run for both crates
      run: |
        set -euxo pipefail
        # vibeflow-protocol dry-run must succeed end-to-end (no path-dep gymnastics).
        cargo publish --dry-run -p vibeflow-protocol
        # vibeflow dry-run depends on vibeflow-protocol being on the registry,
        # which it now is — so this must also succeed end-to-end (post-v0.1.0
        # the structural blocker from Stage 14 is gone).
        cargo publish --dry-run -p vibeflow

    - name: Verify npm pack from a CLEAN checkout (no pre-built dist)
      working-directory: bindings/npm
      run: |
        set -euxo pipefail
        # Ensure dist/ does not exist; the prepack script should create it.
        rm -rf dist
        npm ci
        # `npm pack --dry-run --json` lists exactly what would be published.
        files=$(npm pack --dry-run --json | python3 -c "
import sys, json
out = json.load(sys.stdin)
print('\n'.join(f['path'] for f in out[0]['files']))")
        echo "$files"
        for required in dist/src/index.js dist/src/index.d.ts LICENSE-MIT LICENSE-APACHE README.md package.json; do
          echo "$files" | grep -qE "^$required$" \
            || { echo "::error::missing $required in npm pack"; exit 1; }
        done
```

**Note:** the `vibeflow` dry-run in CI will fail post-Stage-14-merge until
`vibeflow-protocol@0.1.0` is on the registry — which it is, since v0.1.0
shipped. This assertion is honest about that dependency.

### 2.7 `FORCE_JAVASCRIPT_ACTIONS_TO_NODE24: true` in release.yml

`release.yml` `env:` block gains:

```yaml
FORCE_JAVASCRIPT_ACTIONS_TO_NODE24: true
```

Matches `ci.yml`. Silences the Node.js 20 deprecation warning that fired
on the v0.1.0 release run.

## 3. Workflow

Spec → `superpowers:writing-plans` → senior pre-execution Sonnet review of
the plan vs actual source (per `feedback_senior_review_plans`) →
`superpowers:subagent-driven-development` for the larger items (#2 LICENSE
symlinks across both crates + npm; #4 paste sanitiser with TDD; #6 CI
packaging job — these benefit from fresh-context isolation) **or** direct
inline execution for one-liners (#1 prepack scripts, #3 README edit, #5
SHA256 env var, #7 Node 24 env var). Implementer's judgement at plan time;
default to subagent-driven for tasks touching ≥2 files or with TDD value.

Each task spec+quality dual-reviewed (or combined review for trivial diffs).
Controller runs `git status` after every task per
`lesson_subagent_amend_drift`. Reviewers constrained read-only / no git-fs
mutation per `lesson_review_subagent_destructive`. Implementer prompts
include pasted-evidence requirements per
`lesson_subagent_ignored_publish_guard`.

After all tasks: full CI gate green locally → senior holistic review →
merge `main` → bump workspace `version` from `0.1.0` to `0.1.1` + finalise
`CHANGELOG.md` `[Unreleased]` → `## [0.1.1] - <date>` → human-gated finale
(`cargo publish -p vibeflow-protocol` → `cargo publish -p vibeflow` →
`npm publish` from bindings/npm/ with the existing granular token →
`git tag -a v0.1.1` + `git push origin v0.1.1` triggers release CI →
release CI builds the new AppImage + .sha256, attaches both to the GitHub
Release).

The npm token from v0.1.0 still has scope "All packages" + bypass-2FA;
re-using it for v0.1.1 is fine. (Narrowing it to `vibeflow-protocol`-only
is a separately-tracked nice-to-have, not blocking v0.1.1.)
