# vibeflow v0.1.4 — output throughput: bound per-poll PTY drain (#10)

**Date:** 2026-06-01
**Status:** Design approved (root cause confirmed by measurement), pending spec review
**Issue:** [#10](https://github.com/bjhengen/vibeflow/issues/10)

## Problem

During bursts of rapid agentic output (Claude Code running builds/tests, dumping files/diffs),
vibeflow stutters and feels unresponsive — enough that the user throttled the agent. Since
agent-assisted development is vibeflow's primary use case, this is a core-experience bug.

## Root cause (confirmed by measurement)

The PTY reader thread (`session.rs:192`) reads the OS pipe in 4 KB chunks and pushes each onto an
**unbounded** `mpsc` channel, independent of the main loop. So the producer is never
pipe-backpressured — the backlog accumulates in the channel. Then, once per `about_to_wait`
cycle, `PtySession::poll()` (`session.rs:300`) drains the **entire** channel backlog in a single
synchronous call, parsing it **byte-by-byte** (`parser.advance(&mut term, byte)`, `session.rs:362`).

Headless measurements (200×60 grid, `seq 1 2000000` ≈ 16.9 MB after CRLF translation):

| Probe | Result |
|---|---|
| parse/drain throughput | ~16.9 MB in **1.85 s over 7 polls** → **~9 MB/s**, one poll draining the whole backlog |
| realistic main loop (16 ms frame pace) | 5 cycles, **max single cycle = 2.07 s** |
| `build_cell_instances` (full grid) | 5.6 ms/call (secondary) |

So a multi-MB burst makes a single main-loop cycle block for **hundreds of ms to seconds**
(≈ 120 ms/MB), during which no input is serviced and nothing repaints — the observed freeze.
It is **not** producer throttling and **not** GPU/vsync.

## Fix: per-poll byte budget + prompt re-wake

Bound the work each `poll()` does so a burst can never freeze the main loop; drain the remainder
over subsequent cycles, re-woken immediately so total catch-up stays at full parse throughput
while input + repaint stay live throughout.

### 1. Byte budget in `PtySession::poll()`
- New const `MAX_POLL_BYTES: usize = 64 * 1024` (64 KB).
- The drain loop accumulates the lengths of chunks it pulls; once `consumed >= MAX_POLL_BYTES` it
  stops pulling new chunks (leaving the rest queued) and returns. Chunks are ≤ 4 KB (reader
  buffer), so the effective per-poll cap is `MAX_POLL_BYTES + 4 KB` and no partial-chunk handling
  is needed.
- **Budget rationale:** at the measured ~9 MB/s, 64 KB parses in ~7 ms — comfortably under one
  60 Hz frame (16.7 ms), leaving room for the ~5.6 ms render in the same cycle. So a poll+render
  cycle fits in a frame: the loop stays responsive (~one-cycle, ~7–13 ms input latency) instead of
  freezing. Tunable single const; if parse throughput is later improved it can rise.

### 2. Prompt re-wake when backlog remains
- `poll()` sets a flag when it stops because it hit the budget (not because the channel emptied).
  Expose it as `PtySession::output_pending(&self) -> bool`.
- `App::poll_all` aggregates it; add `App::any_output_pending(&self) -> bool`.
- In `about_to_wait`, if `any_output_pending()`, set `ControlFlow::WaitUntil(now)` (immediate
  re-wake) instead of the normal cadence. winit services pending window events (keyboard) between
  these back-to-back cycles, so catch-up runs at full parse throughput **and** input is
  interleaved. Paints continue to coalesce to vsync via the existing `request_redraw` path, so
  the screen shows smooth incremental progress.

### 3. Coalesce `TermUpdated`
- `poll()` currently pushes a `TermUpdated` per chunk (`session.rs:357`) → many redundant
  `request_redraw` calls + event-vec churn per drain. Emit **one** `TermUpdated` per `poll()` call
  if any pass-through bytes were processed. (StateChanged events from OSC frames stay per-event.)

## Budget knob

Not user-facing config — an internal const. Agent output is the primary workload; the default is
tuned for it, and exposing a knob invites foot-guns. Revisit only if real-world tuning needs it.

## Testing (TDD)

- **Budget bound** (`session.rs`, serial — subprocess): spawn `seq 1 2000000`, let the reader
  queue (brief wait so the channel holds ≫ 64 KB), call `poll()` once, assert it consumed
  ≤ `MAX_POLL_BYTES + 4096` and that `output_pending()` is `true` (more remains) — and that
  repeated polls eventually drain it and reach EOF. (Old behavior: one poll drained everything.)
  `poll()` exposes bytes consumed for the assertion (test-visible accessor or counter).
- **Coalesce**: a poll that processes multiple pass-through chunks yields exactly one
  `TermUpdated`.
- **No regression**: existing poll/OSC/bell/tracker tests stay green (OSC 1338/133/52 interception,
  Died, Bell all still fire under budgeting).
- A retained `#[ignore]`'d parse-throughput probe (no GPU) serves as a manual regression bench;
  the GPU-dependent probes used for this investigation are removed.

## Out of scope (documented, deferred)

- **VT parse batching / higher throughput.** `vte 0.13.1` (via `alacritty_terminal 0.24.2`)
  exposes only byte-at-a-time `Processor::advance(handler, byte: u8)` — no slice API. Raising the
  ~9 MB/s ceiling needs a `vte`/`alacritty_terminal` upgrade (newer `vte` has slice `advance`),
  which is a separate, riskier dependency bump. The byte budget removes the freeze regardless of
  throughput, so this is deferred.
- **OscDispatcher double-pass.** Every byte is scanned by vibeflow's `OscDispatcher::feed` and then
  by `vte` — a second per-byte pass. Collapsing them is risky (OSC interception is load-bearing for
  the headline feature) and deferred to a future throughput investigation.
- **Dirty-region rendering** (the 5.6 ms full-grid `build_cell_instances` per frame). Separate,
  larger effort; not required to fix the freeze.

## Non-goals
- No change to OSC 1338/133/52 handling, tracker behavior, or the reader thread.
- No bounded/blocking channel (would re-introduce producer backpressure; the budget achieves
  responsiveness without changing producer semantics).
